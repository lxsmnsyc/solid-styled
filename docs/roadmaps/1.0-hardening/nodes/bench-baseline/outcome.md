# Outcome: bench-baseline

## Built

- `benchmarks/`: private workspace package `benchmarks`, added to `pnpm-workspace.yaml`. It imports the built `solid-styled/compiler` and `unplugin-solid-styled` from the workspace. No product code changed.
- Bench tool: tinybench 6.2.3. Vitest `bench` runs on tinybench, and the package was already in the lockfile. A plain Node script can be run under `node --cpu-prof` with no vitest workers in the way. Each task reports median, MAD, mean, rme (95%), p99 and samples.
- Fixtures in `benchmarks/fixtures/`:
  - `small.tsx`: one component, one `css` template with one interpolation and nesting (33 lines).
  - `large.tsx`: 50 components, 33 `css` templates and 17 `<style jsx>` elements, with interpolations, nesting, `:global`, `@global`, `@keyframes`, `@media` (2,493 lines). Generated by `scripts/generate-large.ts`.
  - `no-styles.tsx`: a Solid table component that imports nothing from solid-styled (180 lines).
  - `global-heavy.tsx`: one `css` template with a large `@global` block and many `:global(...)` selectors.
- Scripts (run from `benchmarks/`, after `pnpm build` at the root):
  - `pnpm bench`: `compile()` per fixture, and the unplugin `transformInclude` + `transform` hooks on `no-styles`.
  - `pnpm bench:suspects`: each library call on its own, one per suspect from the brief.
  - `pnpm bench:profile`: CPU profile of `compile(large)` x100, then `scripts/attribute.ts` charges every sample inside `compile()` to a stage. Other fixtures: `node --cpu-prof --cpu-prof-dir=profiles profile.ts <fixture> <iterations> && node scripts/attribute.ts profiles`.
  - `pnpm bench:count`: LightningCSS and `browserslistToTargets` calls per `compile()`, sheets emitted, source map size.
  - `pnpm bench:raw-transfer`: checks that oxc raw transfer gives the same AST as JSON transfer.
- For A/B runs in perf-compiler, `profile.ts` prints `<n> ms each`, which bench.py reads:
  `python3 <perf-pass>/scripts/bench.py --dir base=<base>/benchmarks --dir a=<a>/benchmarks --runs 10 --warmup 2 --metric '([\d.]+) ms each' -- node profile.ts large 50`

### Suspects from the brief

All from `pnpm bench:suspects` and `pnpm bench:count` on the quiet machine.

- **browserslist resolved per call: yes.** `preprocess-css.ts` calls `browserslistToTargets(browserslist(query))` on every `preprocessCSS`, which is 2 calls per scoped sheet: 100 calls for `large`. `browserslist('defaults')` is cached inside browserslist (1.2 µs). `browserslistToTargets` is not (12.0 µs per call). One LightningCSS call costs 32.0 µs with cached targets and 45.3 µs with targets per call.
- **Sheets parsed twice: three times, in fact.** Each scoped sheet goes LightningCSS, then css-tree parse + 2 walks + generate, then LightningCSS again (`process-css-template.ts`). `large` makes 100 LightningCSS calls for 50 sheets. css-tree costs 65.5 µs per sheet, twice one LightningCSS call. Only `<style jsx global>` sheets skip the last two steps.
- **Full parse without a solid-styled import: yes.** `compile()` parses, walks the whole AST and builds a hires map for every file. It does so even with no `solid-styled` import, no `<style>` and no `use:solid-styled`. It returns the input code unchanged and a 25.6 kB `mappings` string. `parseSync` + `.program` alone takes 0.437 ms of the 0.774 ms. A string check for `solid-styled` or `<style` takes 0.0024 ms.
- **unplugin filter: it parses every file.** `transformInclude` only matches the path glob. `transform` always calls `compile()`. The unplugin path on `no-styles` costs the same as `compile()` (0.775 ms vs 0.774 ms). The bundler then gets a source map for code that did not change.
- **hires source map cost: real but not the top.** With `large`-shaped edits, edits + toString take 0.009 ms. Adding a hires map makes it 1.05 ms, a low-res map 0.151 ms. On `no-styles` with no edits, the hires map alone is 0.125 ms (16% of that compile).
- **oxc JSON transfer.** `parseSync` returns the AST as JSON and parses it in JS. On `large`: 2.53 ms with JSON transfer, 0.279 ms with `experimentalRawTransfer: true`. `pnpm bench:raw-transfer` shows the same AST (equal `JSON.stringify`) on all 4 fixtures.
- **xxhash: no cost.** It hashes the file name only, once per compile.

### Ranked hotspots and candidate fixes

Gains below come from the numbers above. Each needs its own A/B run in perf-compiler.

1. **No fast path for files without styles.** 100% of the no-styles cost (0.77 ms per file, all parse, walk and map). In a real app most modules have no styles, so this is the largest win per build.
   Fix: in the unplugin `transform`, return `undefined` (no change, no map) when the code contains neither `solid-styled` nor `<style`. Also set the unplugin `transform.filter.code` to the same regex, so Vite 8 and Rolldown skip the JS call. The check must include `<style`: `<style jsx>` compiles without any import. `compile()` itself can keep its contract.
   Expected: no-styles 0.77 ms to about 0.003 ms. No change on styled files.
2. **css-tree pass plus the second LightningCSS pass.** 23.2% + about 10% (half of the LightningCSS share) on `large`.
   Fix (structural): do the scoping in a LightningCSS `visitor` (selectors, `@keyframes`, `animation` values) in a single `transform` call, and drop css-tree. Lower-risk step first: one css-tree walk instead of two, using `visit: 'Atrule'` for the keyframes pass.
   Expected: up to about 30% on `large` for the structural fix. The risk is output bytes: the oracle and snapshots must prove the sheets are equal. JS visitor callbacks also add cost of their own.
3. **oxc JSON transfer.** 16.7% on `large`, about 40% on no-styles.
   Fix: `parseSync(..., { experimentalRawTransfer: true })` when `rawTransferSupported()`, else the current path.
   Expected: about 2.2 ms (-18%) on `large`. Same AST on all fixtures.
4. **browserslist targets per call.** 8.0% on `large`, 15.6% on `small`.
   Fix: cache the targets per query string in a module-level `Map`. Same targets, same output.
   Expected: about 1.0 ms (-8%) on `large`, about 0.024 ms (-15%) on `small`.
5. **Generic AST walk.** `analyze` 10.7% on `large`, 26.2% on no-styles. `eachChild` runs `Object.keys` on every node and checks every value.
   Fix: a per-type child-key table, built lazily from the first node of each type. Leaf keys such as `start`, `end`, `type`, `name`, `raw` and `value` are then never read. Fix 1 already removes most of the no-styles cost.
   Expected: about half of `analyze`, so -5% on `large`.
6. **Hires source maps.** 6.7% on `large`, 16.1% on no-styles.
   Fix: `hires: 'boundary'`, or the default low-res map.
   Expected: about 0.9 ms (-7%) on `large`. This changes the map (not the code) and makes it coarser. The maintainer decides.
7. **Small items, about 2% each on `large`.** Reuse one TextEncoder and one TextDecoder in `preprocess-css.ts` (2.4%). `Ctx.unique()` probes `base_1`, `base_2`, ... from 1 on every call, which is quadratic in the number of sheets (1.7%). Keep a next index per base.

## Gotchas

- Run `pnpm build` at the root before benching. The bench imports `dist/`, not the sources.
- Other agents running tests on the same machine move the numbers by up to 8x. Check `uptime` first, and use bench.py for A/B, since it interleaves the sides.
- `pnpm profile` is a pnpm built-in command. The script is `bench:profile`.
- Raw transfer reserves about 6.4 GB of `arrayBuffers` (address space). RSS after 50 parses of `large` was lower than with JSON (144 MB vs 195 MB). Check the effect on 32-bit and memory-limited CI before relying on it.
- `experimentalRawTransfer` is read by oxc-parser 0.157's JS wrapper but is not in its `ParserOptions` type.
- Fix 1 must keep compiling files that use `<style jsx>` with no import, and files that only use `use:solid-styled`.
- The unplugin `transformInclude` hook is marked deprecated in unplugin 3 in favor of `transform.filter`.
